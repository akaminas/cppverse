## What it is

An *algorithm* is a finite sequence of unambiguous steps that turns some input into the output you want. "Find the week in which an outbreak peaks" is a question; "look at the weeks one by one and remember the largest count seen so far" is an algorithm that answers it. A C++ program is one particular way of writing that algorithm down so that a computer can carry it out.

It helps to keep three things apart (see <Concept id="programs-and-algorithms" />):

- the **model**: the biological assumptions, usually as equations;
- the **algorithm**: the procedure that computes what the model predicts;
- the **implementation**: the code that carries out the procedure.

A model can be computed by several algorithms, and an algorithm can be implemented in any language. This lesson is about the middle layer, and about designing it before you open an editor.

## Why it matters

A computer does exactly what it is told, so every step has to be specified, including the ones that seem too obvious to mention: where the simulation starts, in which order events happen within a year, what happens when a population reaches zero. Writing the algorithm first forces those decisions into the open while they are still cheap to change. A design error found after the code is written is expensive, because other parts of the program have been built on it.

A written algorithm is also something you can discuss. A co-author who does not read C++ can check numbered steps against the biology. A reviewer can check them against the methods section. You can check the code against them, line by line.

## How it works in C++

Designing an algorithm and translating it are two separate activities. The design is done on paper or in plain text. The translation into C++ starts only when every step is clear.

### Decomposition

The core technique is *decomposition*: break the task into a few large steps, then break each step into smaller ones, and stop when every step is either a few lines of code or a standard building block that you already know how to write.

Take an annual plant with a seed bank, censused each spring. Some seeds in the soil germinate; the others stay dormant. A small fraction of seedlings survive to flower, each flowering plant sets seed, and the seed bank (old and new seeds together) loses some seeds over winter. The task "simulate this plant for eight years" decomposes like this:

1. Set the parameters and the initial number of seeds.
2. Repeat for each year:
   1. Germination: split the seed bank into seedlings and dormant seeds.
   2. Establishment: keep the seedlings that survive to flower.
   3. Seed set: each flowering plant adds new seeds to the bank.
   4. Winter: old and new seeds survive with the same probability.
   5. Record the year's numbers.

Each sub-step of step 2 is now a single multiplication. That is the signal to stop decomposing. The *order* of the sub-steps is part of the model: if winter came before seed set, new seeds would escape winter mortality, and the plant would grow faster.

### Pseudocode and flowcharts

*Pseudocode* writes an algorithm in a form halfway between prose and a programming language. It has no compiler and no fixed syntax, but a few conventions keep it readable: name the inputs and outputs, use `←` for "becomes", indent the body of every loop and decision, and use the names of the model's symbols. The seed-bank decomposition in pseudocode:

```text
Input:  germination fraction g, establishment fraction e,
        seeds per flowering plant f, winter survival w,
        initial seed bank S, number of years T
Output: seedlings, flowering plants and seed bank in every year

for year ← 1 to T do
    seedlings ← g × S
    dormant   ← S − seedlings
    flowering ← e × seedlings
    newSeeds  ← f × flowering
    S         ← w × (dormant + newSeeds)
    record year, seedlings, flowering, S
```

A *flowchart* draws the same information as boxes for actions, diamonds for decisions and arrows for the flow of control. Flowcharts are clearest for algorithms with branches and loops that exit early; for straight-line arithmetic, pseudocode is shorter. ### From pseudocode to C++

When the pseudocode is complete, the translation is almost mechanical. Each line becomes one statement, `←` becomes `=`, and the loop becomes a `for` loop (see <Concept id="for-loop" />). Comments in the code carry the step names, so the program can be checked against the design:

### The whole workflow

The program above is the end of a chain that every model in this atlas follows:

1. **Biological hypothesis.** A seed bank lets the plant carry on although only 5% of its seedlings survive to flower.
2. **Equations.** Combining the four steps of one year gives the seed bank next spring,

   $$
   S_{t+1} = w\,\bigl[(1-g)\,S_t + f\,e\,g\,S_t\bigr] = \lambda\,S_t,
   \qquad \lambda = w\,\bigl[(1-g) + f\,e\,g\bigr],
   $$

   where $S_t$ is the number of seeds per square metre in spring of year $t$, $g$ the fraction that germinate, $e$ the fraction of seedlings that survive to flower, $f$ the seeds set per flowering plant, and $w$ the fraction of banked seeds that survive the winter. $\lambda$ is the factor by which the seed bank changes each year (dimensionless).
3. **Algorithm.** The pseudocode above.
4. **C++ code.** `seed_bank_cycle.cpp`.
5. **Output.** With $g = 0.3$, $e = 0.05$, $f = 40$ and $w = 0.8$, the equation predicts $\lambda = 0.8 \times (0.7 + 0.6) = 1.04$. The program's seed bank goes from 200 to 208.0 to 216.3: a 4% increase each year, as predicted.

The last comparison matters. A program whose output agrees with a result worked out by hand is far more trustworthy than one that has merely run without errors.

## A minimal example

Many questions about a simulation are questions about its trajectory: when does it peak, when does it fall below a threshold, what is its average? The most common is finding an extreme value. The algorithm is a *linear scan*: pass through the values once, and remember the position of the largest value seen so far.

```text
Input:  a trajectory x[0], x[1], …, x[T] with at least one value
Output: the index (time step) of the largest value

best ← 0
for t ← 1 to T do
    if x[t] > x[best] then best ← t
return best
```

The program below applies it to a simulated outbreak. Each week, $\beta S_t I_t / H$ hosts become infected and a fraction $\gamma$ of the infected recover, where $S_t$ and $I_t$ are the numbers of susceptible and infected hosts in week $t$, $H = 500$ is the (constant) number of hosts, $\beta = 0.9$ is the number of infections one infected host causes per week in a fully susceptible population, and $\gamma = 0.4$ is the fraction of infected hosts that recover each week.

<Example file="algorithms/outbreak_peak.cpp" mark="29-37" />

The function `indexOfMaximum` returns the *index*, which here is the week, rather than the number of infected hosts. The size is then `infected[peak]`. The comment states a precondition: an empty trajectory has no peak, and `values[best]` would read outside the vector. A careful program checks this (see <Concept id="debugging" />).

Sorting the trajectory and taking the last element would also find the largest value, but it does more work than needed and destroys the information you wanted: after sorting, the position of the peak in time is lost.

<Callout kind="tip" title="The standard library version">
`std::max_element` from `<algorithm>` performs the same scan and returns an iterator to the largest element. `std::distance(v.begin(), std::max_element(v.begin(), v.end()))` gives the index. Writing the loop yourself once is the best way to understand what it does; see <Concept id="standard-algorithms" /> for the library versions.
</Callout>

### Recurring building blocks

Decomposition keeps arriving at the same small problems. Most of them have a well-known, efficient algorithm that you can reuse:

- **Extremes**: largest or smallest value and where it occurs (the scan above). Peak abundance, the generation of minimum genetic diversity, the hottest day.
- **Sums and means**: one pass with a running total. Total population over all stages, mean final size over replicates.
- **Counting with a condition**: one pass with a counter. The number of generations in which the population was below a threshold.
- **First occurrence**: a scan that stops early. The first year of quasi-extinction.
- **Weighted choice**: pick an item with probability proportional to its weight, for example a parent in proportion to its fitness. This needs running sums of the weights and a random number; see <Concept id="weighted-lottery" />.

When a step of your design turns out to be one of these, you can stop decomposing it.

## In biological modelling

Write the pseudocode of a model before writing its code, and keep it. It belongs in the methods section, in the supplementary material, or in an ODD protocol (Overview, Design concepts, Details), the standard way of describing individual-based models. Use the same names in the pseudocode, the code and the paper, so that a reader can follow a symbol from one to the next.

Pay most attention to the *order* of steps within a time step. Whether mortality comes before or after reproduction, or whether all individuals update at once or one by one, changes the predictions of a model, sometimes qualitatively. The lessons on <Concept id="update-rule" /> and <Concept id="update-order" /> return to this.

Decompose until each step is a few statements or a known building block, and no further. The seed-bank program needs only one level of decomposition; an individual-based model may need three or four, and each level often becomes a function.

## Common mistakes

- **Coding before the algorithm is clear.** If you cannot write the step in one sentence of pseudocode, you are not ready to write it in C++.
- **Ambiguous steps.** "Update the population" hides decisions: which individuals, in which order, using which state? Write the decision down.
- **Ignoring the edge cases.** What should the scan return for an empty trajectory? What does the model do when a population reaches zero? Decide in the design, not when the program crashes.
- **Off-by-one counts.** A run of $T$ generations has $T + 1$ states, $x_0$ to $x_T$. The scan starts its comparisons at index 1 because index 0 is the initial candidate.
- **Doing more work than the question needs.** Sorting to find a maximum, or storing every value when only a running total is needed.

<details>
<summary>Worked answer for exercise 1</summary>

```text
Input:  trajectory x[0], …, x[T]; threshold Nc
Output: the first t with x[t] < Nc, or "none"

for t ← 0 to T do
    if x[t] < Nc then return t
return "none"
```

In C++, "none" needs a value that cannot be a generation. One option is to return `x.size()`, which is one past the last valid index:

```cpp
std::size_t firstBelow(const std::vector<double>& x, double threshold) {
    for (std::size_t t = 0; t < x.size(); ++t) {
        if (x[t] < threshold) return t;
    }
    return x.size();  // never fell below the threshold
}
```

The scan stops at the first match, so unlike the maximum it does not always visit every value.
</details>
