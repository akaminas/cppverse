## What it is

A *class* is a user-defined type that combines data with the functions allowed to operate on that data. You have used classes from the first lesson: `std::cout`, `std::string` and `std::vector` are all objects of library classes. You call their *member functions* with a dot (`v.push_back(x)`, `s.find('-')`), and you never touch their internal data directly. That is deliberate, and this lesson shows how to give your own types the same protection.

In C++, `class` and `struct` define exactly the same kind of type. The only difference is the default *access*: members of a `struct` are public (usable by any code) unless you say otherwise; members of a `class` are private (usable only by the class's own member functions) unless you say otherwise.

## Why it matters

A struct with public members, as in <Concept id="structs" />, lets any line of the program set any member to any value. For a parameter set that is fine. For many model types it is not, because some values are simply invalid: a population of −3 individuals, a survival probability of 1.4, a list of individuals whose stored count differs from the actual number. Such a state never arises from the biology; it arises from a bug. If it can arise anywhere in the code, you have to check everywhere.

A class turns that around. Its data are private, and every change goes through a small number of public member functions. If those functions keep the data valid, the data *are* valid, everywhere and always. A condition of this kind is called a *class invariant*, and keeping it is the main reason to write a class.

### Access: public and private

The labels `public:` and `private:` divide the members into the *interface*, available to everyone, and the *hidden* part, available only inside the class. Each label applies until the next one. A common layout puts the public member functions first, because they are what a reader of the class needs, and the private data last.

Private does not mean secret or secure; it means that the compiler rejects any use from outside the class:

<Example file="data/class_private_access.cpp" mark="16" />

GCC reports `'int Population::size_' is private within this context`. The program cannot even be built with the invariant broken.

### Member functions

A member function is declared inside the class and called through an object: `beetles.addBirths(30)`. Inside the function, the data members of *that* object are available by their names, so `size_ += births;` changes the `size_` of `beetles` and of no other `Population`.

A member function that only reads the object is marked `const` after its parameter list: `int size() const;`. The compiler then refuses any change to the data members inside it, and only `const` member functions may be called on a `const` object or through a `const` reference. Mark every reading function `const`; forgetting it makes the class unusable in code that, correctly, passes objects as `const Population&`.

Member functions can be defined in two places. A short function can be written directly inside the class body, as in `int size() const { return size_; }`. Longer ones are usually only *declared* in the class and *defined* afterwards under their qualified name, `Population::removeDeaths`, with the scope resolution operator `::` (the same operator as in `std::cout`). Both forms mean the same.

### Default member initialisers

A data member can be given an initial value where it is declared: `int size_ = 0;`. Every new object then starts in a valid state. Without it, a `Population` created as `Population beetles;` would contain an uninitialised `int`, and the first `addBirths` would add to whatever bits happened to be in memory.

<Callout kind="manual" title="Initialise every data member">
The manual's first class example adds to a private member that is never initialised, so its output is undefined. Since C++11 a default member initialiser (`double reserve = 0.0;`) fixes this in one line. The usual alternative, a *constructor* that sets the members when the object is created, is the subject of <Concept id="constructors" />. The manual also leaves its reading member functions without `const`; mark them `const` as shown here.
</Callout>

### Interface, implementation, application

A class naturally splits code into three parts:

1. the **interface**: the class definition, which says *what* can be done with a `Population`;
2. the **implementation**: the definitions of the member functions, which say *how*;
3. the **application**: the code that uses objects of the class, such as `main`, which may rely on the interface only.

In larger programs the three go into different files: the class definition in a header `population.hpp`, the member definitions in `population.cpp`, and the application in `main.cpp` (see <Concept id="multiple-files" />). Even in a single file, keeping them in this order makes the class easy to read and to check.

### Objects as values

Objects of your own classes behave like `int`s and `double`s: they can be copied, assigned, passed to functions and returned from them.

- **Copying** creates a new, independent object with the same member values: `const Population before = island;`. Later changes to `island` do not affect `before`.
- **Assignment**, `mainland = island;`, overwrites every data member of `mainland` with the corresponding member of `island`.
- **Passing by value**, `int sizeIfHalved(Population p)`, gives the function its own copy. Whatever it does to `p` leaves the caller's object untouched.
- **Passing by reference**, `void harshWinter(Population& p)`, lets the function change the caller's object (<Concept id="references" />).
- **Passing by const reference**, `const Population& other`, gives read-only access without a copy. This is the normal way to pass objects that are not cheap to copy, such as anything containing a vector (<Concept id="const-reference" />).
- **Returning** an object from a function, as `founders(40)` does, hands the new object to the caller.

The compiler writes the copy and assignment operations for you: they copy the members one by one. That is exactly right for classes whose members are numbers, strings and vectors. (Classes that manage a resource by hand need more care, which is one reason this site never does that; see <Concept id="pointers-ownership" />.)

<Example file="data/class_objects.cpp" mark="19-21,32-39,43,55" />

`isLargerThan` takes another `Population` and reads its private `size_`. This is allowed: access control is per *class*, not per object, so a member function may use the private members of any object of its own class. It is how comparisons, merges and other operations between two objects of the same type are written.

Copies are also how a model takes a *snapshot*. A simultaneous update reads only from the old state; the simplest correct implementation copies the state, computes every new value from the copy, and only then replaces the state (<Concept id="update-order" />).

## In biological modelling

When is a struct enough, and when does a class help? A useful rule:

- **A struct** when every combination of member values is acceptable, or when the type is a passive record: a parameter set, a sample, the output of a function. `struct Parameters { double r; double K; };` needs no protection worth the extra code.
- **A class** when some combinations are invalid, or when members depend on each other. A population size that must stay non-negative; a probability that must stay in [0, 1]; a landscape whose vector of patches must always have `rows * cols` elements; a population of individuals that keeps a running total of biomass that must equal the sum over individuals. The class makes the rule part of the type.

Classes also give the code the shape of the model. An individual-based model reads naturally as interacting objects: `plant.grow(light)`, `plant.isAlive()`, `patch.colonise(seeds)` (see <Concept id="individual-representation" />). Once the member functions of each class are correct, the main loop can be written, and checked, at the level of the biology.

## Common mistakes

- **Uninitialised data members.** Give each member a default initialiser (or a constructor).
- **Missing `const` on reading member functions.** The class then cannot be used through `const` references.
- **Forgetting the class qualifier.** Writing `int size() const { … }` outside the class defines a free function, which then fails to compile because `size_` is unknown, or, worse, compiles if a global of that name exists. Write `int Population::size() const`.
- **Getters and setters for everything.** A public `setSize(int)` that accepts any value gives the invariant away again. Offer operations that mean something in the model (`addBirths`, `removeDeaths`) rather than raw access to each member.
- **Forgetting the semicolon** after the closing brace of the class.
- **Passing objects by value by accident.** `void report(Population p)` copies the whole object at every call. For anything containing a vector, use `const Population&`.
