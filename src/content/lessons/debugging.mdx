## What it is

A *bug* is any difference between what a program does and what you meant it to do. *Debugging* is finding and removing bugs, and it is easier when you know which kind you are dealing with:

- **Compile-time errors.** The code is not valid C++: a missing semicolon, a misspelt name, a type mismatch. The compiler stops and reports roughly where (see <Concept id="compiler-diagnostics" />).
- **Link errors.** Every file compiles, but the linker cannot assemble the program: a function was declared but never defined, a library was not linked, or something was defined twice. The message names the missing or duplicated symbol (see <Concept id="compilation" />).
- **Run-time errors.** The program builds, then crashes, aborts, throws an exception that nobody catches, or never finishes. The symptom is obvious; its cause can be far away from where the program stops.
- **Silent errors.** The program runs to completion and produces output, and the output is wrong. Nothing tells you so.

For a scientist the last kind is the most dangerous. A crash costs an afternoon; a silent error can end up in a figure, a thesis or a paper.

## Why it matters

Even experienced programmers introduce roughly one bug for every few hundred lines of new code. A model of a few hundred lines therefore very probably contains at least one when it first runs, and the program cannot tell you which of its numbers are wrong. Error checking has to be designed in, alongside the algorithm, rather than added once something looks odd.

## How it works in C++

The tools below catch different kinds of error at different times. Use them together.

### assert: checking invariants while you develop

An *invariant* is a statement that must be true at a given point if the program is correct. Models are full of them, and they come from the biology:

- densities and counts are never negative;
- probabilities and fractions lie between 0 and 1;
- proportions over all stages sum to 1;
- a process that only moves individuals, such as dispersal, neither creates nor destroys them.

The macro `assert` from `<cassert>` checks such a statement. If the condition is true, nothing happens. If it is false, the program prints the condition, the file, the line and the function, and stops immediately by calling `std::abort`. The program below asserts three invariants of a source–sink model, in which a sink patch ($R < 1$) persists only through immigration from a source:

<Example file="algorithms/dispersal_invariants.cpp" mark="21,23,29" />

With the parameters as given, every assertion holds and the program prints the trajectory. Change `m` on line 34 to `1.2` and run it again. The first assertion fails before any arithmetic is done, with a message such as

```text
dispersal_invariants: dispersal_invariants.cpp:21: Patches disperse(const Patches&, double):
Assertion `m >= 0.0 && m <= 1.0 && "the dispersal fraction must be a probability"' failed.
Aborted (core dumped)
```

The exact wording differs between compilers and systems, but it always gives the location. Two details of the example are worth copying:

- **`&& "message"`.** A string literal is always true, so adding it to the condition does not change the test; it only makes the message readable.
- **A tolerance in the conservation check.** Floating-point arithmetic rounds, so `total(next) == total(n)` might fail for a correct program. Line 23 allows a relative difference of $10^{-12}$, many times the rounding error of one step and far smaller than any real bug would produce.

Assertions are a development tool. Defining the macro `NDEBUG`, by compiling with `-DNDEBUG` or writing `#define NDEBUG` before `#include <cassert>`, removes every `assert` from the program: the conditions are not even evaluated. Release builds usually define it (CMake's Release configuration does). Two rules follow:

- Never put work that must happen inside an `assert`. In `assert(++generation <= maxGenerations);` the increment disappears with `NDEBUG`.
- Never use `assert` to check things a *user* can get wrong, such as a parameter file. Those checks must stay active in every build: use exceptions for them (see <Concept id="exceptions" />).

### static_assert: checking at compile time

Some facts about a program are known before it runs: the number of stages, the size of an array, the type used for densities. `static_assert(condition, "message")` checks such a condition during compilation and stops the build with the message if it is false. It costs nothing at run time and cannot be switched off.

<Example file="algorithms/static_assert_stages.cpp" mark="11-14" />

A model was extended from three to four stages, but the list of labels was not updated. Without the `static_assert`, the program would compile and quietly print three labels for four stages. With it, the compiler reports `static assertion failed: every stage needs exactly one label`. The condition must be a constant expression, which is why both quantities are declared `constexpr`.

### Printing the state

The quickest way to look inside a running model is still to print its state. A few habits make this far more useful:

- Print to `std::cerr`, so that diagnostic lines do not mix with the data written to `std::cout` or to a file.
- Print enough digits. `std::setprecision(17)` shows a `double` in full; the default six significant digits can hide the difference you are looking for.
- Print *selectively*: one generation in a hundred, or only when something unusual happens, such as a density above a plausible bound.
- Print the inputs of the failing step, not only its result: the state, the parameters and the time.

### Debuggers

A *debugger* runs your program under its control. It can stop the program at a chosen line, show every variable at that moment, and continue one line at a time. For C++ the common debuggers are **gdb** (with GCC, mostly on Linux and Windows) and **lldb** (with Clang, the default on macOS). Compile with debugging information and without optimisation, so that every variable is still there to inspect:

```text
g++ -std=c++17 -g -O0 dispersal_invariants.cpp -o dispersal_invariants
```

The essential operations are the same in every debugger:

| Operation | What it does | gdb | lldb |
|---|---|---|---|
| Breakpoint | Stop just before a line or a function runs | `break grow` or `break dispersal_invariants.cpp:44` | `b grow` |
| Conditional breakpoint | Stop only when a condition holds | `break dispersal_invariants.cpp:44 if t == 5` | `breakpoint set -l 44 -c 't == 5'` |
| Run, continue | Start the program; carry on to the next stop | `run`, `continue` | `run`, `continue` |
| Step over | Execute the current line, including any calls, as one step | `next` | `next` |
| Step into | Enter the function called on the current line | `step` | `step` |
| Step out | Finish the current function and return to its caller | `finish` | `finish` |
| Inspect | Show a variable or expression | `print n` | `p n` |
| Watch | Stop whenever a variable changes | `watch n.sink` | `watchpoint set variable n.sink` |
| Call stack | Show which functions led to this point | `backtrace` | `bt` |

After a crash, `backtrace` shows the line at which the program stopped and the chain of calls that led there, with their arguments. That is usually the fastest route from a crash to its cause.

In **Visual Studio Code** the same operations are buttons. With the C/C++ extension installed, click in the margin to set a breakpoint (right-click for a condition), start debugging with F5, and use the toolbar to step over, into and out. The Variables panel shows locals, the Watch panel evaluates expressions you choose, and the Call Stack panel shows the backtrace. The extension needs a `launch.json` file that names the program and the debugger:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug model",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/dispersal_invariants",
      "cwd": "${workspaceFolder}",
      "MIMode": "gdb"
    }
  ]
}
```

On macOS, use `"MIMode": "lldb"`.

### Sanitizers

Some of the worst run-time errors are *undefined behaviour*: reading past the end of a vector with `[]`, using memory after it has been freed, or overflowing a signed integer. The C++ standard places no requirement at all on what such a program does. It may crash, it may print plausible numbers, or it may behave differently with another compiler. Typical examples in model code:

```cpp
for (std::size_t t = 0; t <= trajectory.size(); ++t) {  // <= reads one element too many
    total += trajectory[t];
}
```

GCC and Clang can build the program with *sanitizers* that check for such errors as it runs:

```text
g++ -std=c++17 -g -fsanitize=address,undefined model.cpp -o model
```

AddressSanitizer stops the program at the first out-of-bounds access and reports the offending line, the size of the memory block that was overrun and where it was allocated. UndefinedBehaviorSanitizer reports signed overflow, invalid shifts, division by zero in integers and similar errors. The program runs two to three times more slowly, which is perfectly acceptable while testing. Sanitizers are available with GCC and Clang on Linux and macOS; on Windows, MSVC offers AddressSanitizer with `/fsanitize=address`.

Two cheaper alternatives catch the commonest case, an index out of range: `v.at(i)` checks the index and throws `std::out_of_range`, and with GCC's standard library, compiling with `-D_GLIBCXX_ASSERTIONS` makes `operator[]` check its index too.

### Warnings come first

Before any of these tools, let the compiler help. Build with `-Wall -Wextra -Wpedantic`, read every warning, and fix it. Warnings point at code that is legal but probably wrong: an unused variable that was meant to be used, a comparison between signed and unsigned values, a variable used before it is initialised. Every program on this site compiles with `-Werror`, which turns each warning into an error.

## In biological modelling

Write the invariants of a model down when you design it, and put them into the code as assertions while you develop it. They document the assumptions, and they catch the update-order mistakes, sign errors and unit slips that otherwise produce silent errors. Good candidates include non-negativity, probabilities in $[0, 1]$, conservation in closed systems, and totals that must match, such as the sum of the stages and the population size.

A model that passes its assertions can still be wrong; assertions only check what you thought of. Combine them with verification against known results, such as closed-form solutions and equilibria (see <Concept id="verification" />), and turn every bug you find into a test that would have caught it (see <Concept id="testing-reproducibility" />).

When something goes wrong, debug like an experimentalist. Reproduce the error with the smallest input that shows it; form a hypothesis about the cause; test it with a breakpoint, a print or an assertion; change one thing at a time; and keep a record of what you tried.

## Common mistakes

- **Trusting a program because it does not crash.** Absence of a crash is not evidence of correctness.
- **Side effects inside `assert`.** They disappear with `NDEBUG`.
- **Asserting exact floating-point equality.** Rounding makes `==` fail for correct code; use a tolerance scaled to the magnitude of the values.
- **Using `assert` for input validation.** Parameter files and command-line arguments must be checked in every build; throw an exception instead.
- **Debugging an optimised build.** With `-O2`, variables are often "optimised out" and lines execute out of order. Debug with `-g -O0`.
- **Changing several things at once.** If the bug disappears, you do not know which change fixed it, or whether it is merely hidden.
