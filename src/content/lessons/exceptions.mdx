## What it is

An *exception* is an object that a function *throws* when it cannot do its job. Throwing abandons the rest of the function, and of every function that called it, until the program reaches a matching *handler*:

```cpp
double survivalProbability(int survivors, int marked) {
    if (marked <= 0) throw std::invalid_argument("no individuals were marked");
    if (survivors < 0 || survivors > marked) {
        throw std::invalid_argument("survivors must lie between 0 and the number marked");
    }
    return static_cast<double>(survivors) / marked;
}

try {
    const double s = survivalProbability(31, 0);
    std::cout << "survival " << s << '\n';        // skipped
} catch (const std::invalid_argument& e) {
    std::cerr << "cannot estimate survival: " << e.what() << '\n';
}
```

The `try` block contains the code that might fail. The `catch` block that follows handles one type of exception; `e.what()` returns the message given when it was thrown. If nothing goes wrong, the handler is skipped.

## Why it matters

The checks in <Concept id="debugging" /> catch mistakes made by the *programmer*, and they vanish from release builds. Many errors are not programming mistakes at all: a parameter file with a missing value, a survival probability typed as 1.3, a data file that does not exist, a numerical method that fails to converge. They can occur in any run, so the checks must be active in every build.

Exceptions also separate *detecting* an error from *deciding what to do about it*. The function that reads a parameter knows that the value is impossible, but not whether the right response is to skip one scenario of a sensitivity analysis or to stop the whole run. The caller knows. An exception carries the information up to the code that can decide, and unlike a returned error code it cannot be silently ignored.

## How it works in C++

### Throwing, propagating and catching

The rules, in the order they apply:

1. `throw expression;` creates an exception object and leaves the current function immediately. The statements after the `throw` do not run.
2. The exception passes up the chain of calls (it *propagates*) until it reaches a `try` block with a handler for its type. On the way, every local object is destroyed, in reverse order of construction. This is called *stack unwinding*.
3. The handlers after a `try` block are tried in order, and the first whose type matches runs. A handler for a base class also matches derived classes.
4. After the handler finishes, execution continues *after the whole try–catch construct*, not after the `throw`. There is no way back into the function that threw.
5. If no handler matches anywhere, the program calls `std::terminate`, which by default aborts it.

### The standard exception types

The standard library defines a family of exception classes, all derived from `std::exception` (in `<exception>`). The ones you will throw yourself are declared in `<stdexcept>`:

| Class | Use it for | Thrown by the library, for example |
|---|---|---|
| `std::logic_error` | Errors that the program could in principle have prevented: a violated precondition | |
| └ `std::invalid_argument` | An argument that has an impossible value: $R_0 < 0$, a probability of 1.3 | `std::stod("abc")` |
| └ `std::out_of_range` | An index or key outside the valid range | `std::vector::at`, `std::map::at` |
| └ `std::domain_error`, `std::length_error` | A value outside a function's mathematical domain; a size that is too large | `std::vector::reserve` (`length_error`) |
| `std::runtime_error` | Errors that can only be detected while running: a missing file, malformed input, no convergence | |
| └ `std::range_error`, `std::overflow_error`, `std::underflow_error` | Results that cannot be represented | |

`std::bad_alloc` (from `<new>`) is thrown when memory runs out. Every class has a constructor that takes a message as a `std::string`, and every one provides `what()`.

Two rules about catching:

- **Catch by `const&`.** `catch (const std::exception& e)` binds to the thrown object without copying it. Catching by value, `catch (std::exception e)`, copies only the base-class part (the object is *sliced*), so a `std::invalid_argument` loses its type and, typically, its message.
- **Order handlers from specific to general.** `catch (const std::invalid_argument&)` must come before `catch (const std::exception&)`, or the general handler would always win. A final `catch (...)` catches anything at all, including types that are not exceptions, but it cannot tell you what was thrown.

<Callout kind="manual" title="Throw exception classes, not strings">
The course manual throws `std::string` messages and catches them by non-const reference. That works, but it does not fit the standard hierarchy: a `catch (const std::exception&)` in `main` will not catch a string. Throw a class derived from `std::exception`, catch by `const&`, and include `<stdexcept>` for `std::logic_error`, `std::runtime_error` and their relatives.
</Callout>

The inner `try` (lines 45–52) catches it, records the rejection and moves on to the next scenario. One impossible scenario should not end a sensitivity analysis of a hundred.
- **Fatal, handled in `main`.** If a line cannot be read at all, `readScenario` throws `std::runtime_error` (line 34), which the inner handler does not catch, because it is not an `invalid_argument`. A line such as `grassland 2.0 forty 5` would stop the program with `fatal error: scenario 'grassland': expected three numbers`.

Notice also what is *not* treated as an error: a scenario with $R_0 < 1$ is valid and simply predicts extinction. An exception means "this computation cannot be carried out", not "the result is biologically interesting".

### Validating model parameters on input

Parameters arrive from files, command lines and other people's scripts, so check them where they enter the program, before any simulation runs. Good checks:

- test the biological constraint, not just the type: probabilities in $[0, 1]$, rates and carrying capacities positive, survival out of a stage at most 1 (see <Concept id="matrix-models" />);
- write `!(x > 0.0)` rather than `x <= 0.0` when a NaN must be rejected too, since every comparison with NaN is false;
- say in the message which parameter, which value and which rule;
- add context when you translate a library exception. `std::stod` reports only `stod` as its message; catch it and throw a message that names the parameter:

```cpp
double parseParameter(const std::string& name, const std::string& text) {
    try {
        std::size_t used = 0;
        const double value = std::stod(text, &used);
        if (used == text.size()) return value;
    } catch (const std::exception&) {
        // std::invalid_argument or std::out_of_range from std::stod
    }
    throw std::invalid_argument("parameter " + name + ": '" + text + "' is not a number");
}
```

The check `used == text.size()` rejects input such as `2.5x`, which `std::stod` would otherwise read as 2.5 without complaint.

### Ending a program: return, std::exit and std::abort

There are three ways to stop a C++ program, and they differ in what is cleaned up:

- **Returning from `main`** ends the program normally. All local objects are destroyed, open files are flushed and closed, and the return value becomes the exit status (`EXIT_SUCCESS` or `EXIT_FAILURE` from `<cstdlib>`).
- **`std::exit(status)`** ends the program from anywhere. It destroys objects with static storage duration and flushes the C streams, but it does **not** unwind the stack: local objects of the functions still running are never destroyed. A local `std::ofstream` that still holds buffered output can lose it.
- **`std::abort()`** ends the program immediately and abnormally, with no clean-up at all. A failed `assert` calls it, and so does `std::terminate` for an uncaught exception.

The course manual describes `exit()` as a normal termination that clears all variables. Static objects are indeed destroyed, but local (automatic) objects are not, as the program above shows. Returning from `main` is the clean way to end a program with an error status.

## In biological modelling

A typical simulation program has three layers of error handling:

1. **At the boundary**, where parameters and data enter: validate everything, and throw `std::invalid_argument` or `std::runtime_error` with a precise message.
2. **In the numerical core**: throw when a method cannot produce an answer, for example when the power method for a projection matrix does not converge within its iteration cap (see <Concept id="power-iteration" />) or a stochastic simulation finds that no event can occur (see <Concept id="gillespie" />).
3. **In `main`**: catch `const std::exception&`, then `...`, report to `std::cerr` and return `EXIT_FAILURE`.

In between, most code does not need any `try` at all. Exceptions pass through it, and stack unwinding releases what it held.

For a batch of scenarios, decide in advance which errors end the batch and which skip one scenario, and make the program report both. A results file that silently omits the scenarios that failed is itself a silent error.

## Common mistakes

- **Using `assert` for input checks.** It disappears with `NDEBUG`; input can be wrong in any build.
- **Throwing strings or integers.** They are not caught by `catch (const std::exception&)` and carry no type information.
- **Catching by value**, which slices the exception.
- **A general handler before a specific one.** `catch (const std::exception&)` first means `catch (const std::invalid_argument&)` after it never runs.
- **Swallowing exceptions.** `catch (...) {}` with an empty body hides every error, including the ones you did not anticipate.
- **Using exceptions for expected outcomes**, such as extinction or reaching the end of a file. Use ordinary control flow for those.
- **Calling `std::exit` deep inside a program.** Local objects are not destroyed and their buffered output can be lost; throw instead.
- **Forgetting the message.** "error" helps nobody; "survival out of vegetative exceeds 1" tells the user what to fix.
