## What it is

You now know enough C++ to write a complete, honest simulation: one that takes its parameters from outside, refuses nonsense, runs a model, writes a well-documented output file and checks its own result. This lesson assembles such a program from the pieces of the earlier lessons. It introduces almost nothing new; instead it shows how the pieces fit together, and where each one came from.

The program is *procedural*: it is organised around functions that act on data held in structs. The next part of the course, starting with <Concept id="classes" />, organises programs around objects instead, and this program is the baseline against which that design can be judged.

## Why it matters

Almost every simulation, however large, has the same skeleton:

1. **parameters**, fixed during a run;
2. a **state**, which changes;
3. an **update rule** that maps the state at time $t$ to the state at $t + 1$;
4. a **loop** that applies the rule and records the trajectory;
5. **input** and **validation** of the parameters;
6. **output** of the trajectory, with enough metadata to reproduce it.

Recognising the skeleton makes unfamiliar model code readable, and keeping to it makes your own code checkable.

## How it works in C++

### The model

Many populations have a juvenile stage that does not reproduce. A minimal model in discrete time keeps two numbers, juveniles $J_t$ and adults $A_t$, counted once per generation:

$$
J_{t+1} = \frac{b\,A_t}{1 + A_t/M}, \qquad A_{t+1} = s_j\,J_t + s_a\,A_t
$$

- $b$: juveniles recruited per adult when adults are scarce;
- $M$: the adult density at which recruitment per adult is halved (competition among breeders);
- $s_j$: the probability that a juvenile survives to become an adult; the others die;
- $s_a$: the probability that an adult survives a generation.

Two quantities follow from the equations and give the program something to check. An adult lives on average $1/(1 - s_a)$ generations and produces $b$ juveniles in each, of which a fraction $s_j$ mature, so at low density each adult replaces itself

$$
R_0 = \frac{b\,s_j}{1 - s_a}
$$

times. If $R_0 > 1$ the population grows from low numbers and settles at the equilibrium obtained by setting $J_{t+1} = J_t$ and $A_{t+1} = A_t$:

$$
A^* = M\,(R_0 - 1), \qquad J^* = \frac{(1 - s_a)\,A^*}{s_j}.
$$

Two design choices are worth making explicit:

- **The model knows nothing about input and output.** `step` and `simulate` neither read nor print. They can be tested, reused in a parameter sweep, or moved into their own file pair (<Concept id="multiple-files" />) without change.
- **Validation happens once, early.** After `validate(p)` the rest of the program may assume sensible parameters. The test is written as "all conditions hold" rather than "any condition fails", so that a `nan` parameter, for which every comparison is false, is rejected too.

## What Module 11 adds

The review module of the course manual also gathers a few smaller features that did not fit elsewhere. Each is worth knowing when you read other people's code.

### Three ways to initialise

```cpp
int clutch = 7.6;    // copy initialisation: silently becomes 7
int clutch2(7.6);    // direct initialisation: also 7
int clutch3{7.6};    // brace initialisation: error, narrowing from double to int
```

The three forms are not equivalent. Braces refuse *narrowing* conversions, those that may lose information, which is why this site prefers them. One more trap: `Parameters p();` with empty parentheses does not create an object at all but declares a function returning `Parameters`. Write `Parameters p;` or `Parameters p{};`. See <Concept id="initialisation" />.

<Callout kind="manual" title="Not all equivalent">
The course manual presents the three initialisation forms as equivalent. They differ in exactly the case that matters for models, a `double` value stored in an integer variable, where only the brace form reports the mistake.
</Callout>

### Unsigned literals

The suffix `u` makes an integer literal unsigned: `40u` has type `unsigned int`. Mixing signed and unsigned values in a comparison converts the signed one to unsigned, with surprising results:

```cpp
const int change = -1;
if (change < 1u) { /* never reached: -1 becomes 4294967295 on common systems */ }
```

GCC (with `-Wall`) and Clang (with `-Wextra`) warn about such comparisons. The same conversion happens when a signed index is compared with `v.size()`, which is why loops over vectors use `std::size_t`. See <Concept id="literals-constants" /> and <Concept id="numeric-limits" />.

### Sharing a variable between files: `extern`

A global variable defined in one source file can be used in another if that file declares it with `extern`:

```cpp
// settings.cpp
int verbosity = 1;          // the definition: storage lives here

// settings.hpp, included wherever verbosity is used
extern int verbosity;       // a declaration only: "defined in another file"
```

This is the variable counterpart of a function prototype, and obeys the same one-definition rule (<Concept id="multiple-files" />). Use it sparingly: a mutable global can be changed from anywhere, which makes a model hard to reason about. Pass parameters explicitly, as `two_stage_sim.cpp` does, and give shared constants a single definition in a header with `inline constexpr`.

### `(void)` in a parameter list

```cpp
int countAdults(void);      // C style
int countAdults();          // C++ style: the same declaration
```

In C an empty list once meant "unspecified parameters", so `(void)` was needed to say "none". In C++ the two forms mean the same; write `()`.

### `std::make_pair`

```cpp
#include <utility>
std::vector<std::pair<int, double>> samples;           // (generation, adults)
samples.push_back(std::make_pair(10, 49.45));          // older style
samples.push_back({20, 72.70});                        // braces do the same
std::pair first{0, 10.0};                              // C++17 deduces pair<int, double>
```

`std::make_pair` creates a pair whose types are deduced from the arguments. It is common in older code; braces and C++17 class template argument deduction make it rarely necessary now. See <Concept id="pairs" />.

### A vector from part of another

A vector can be constructed from a *range* of another container, given by two iterators: the first element to copy and the position just after the last.

```cpp
const std::vector<State> trajectory = simulate(p);
const std::vector<State> lastTen(trajectory.end() - 10, trajectory.end());   // needs size() >= 10
```

`begin()` and `end()` and what you can do with them are the subject of <Concept id="iterators" />.

### The fourth stream state

Besides `good()`, `eof()` and `fail()`, a stream has `bad()`: true when the stream itself has lost integrity, for instance after a read error from the device or a failed write to a full disk. `fail()` is also true in that case, which is why `two_stage_sim.cpp` can check `out.fail()` after closing its file. See <Concept id="stream-state" />.

## In biological modelling

This program is a template you can reuse. Changing the model means changing `Parameters`, `State`, `step`, `validate` and the column names; the loop, the input handling and the output machinery stay as they are. The same skeleton carries through the first capstone (<Concept id="capstone-a" />), and the matrix models of <Concept id="matrix-models" /> are the linear relatives of this model.

The final check against $R_0$ and the equilibrium is the most valuable part of the output. A simulation that reproduces a result derived independently from the equations has passed a first test of <Concept id="verification" />; one that does not is wrong somewhere, however plausible its figures look.

## Common mistakes

- **A model function that prints.** Keep input and output out of `step` and `simulate`, so that they can be tested and reused.
- **Validation scattered through the program**, or missing altogether. Validate once, right after reading.
- **Updating in place.** Writing `s.adults = …` before computing the recruits from `s.adults` changes the model.
- **Unexplained magic numbers.** Every number in the update rule should be a named parameter with a unit and a comment.
- **Trusting the output without a check.** Compare with something you can derive: an equilibrium, a closed form, a limiting case.
