## What it is

A function is *recursive* when it calls itself. That sounds circular, but it works when each call hands a smaller version of the problem to the next one, and when there is a smallest version, the **base case**, that is answered directly without a further call.

Many biological quantities have exactly this structure. The descendants of a founder over $n$ generations are its offspring, plus the descendants of each offspring over the remaining $n - 1$ generations. The species in a clade are the species in each of its subclades, added up. The definition refers to itself, and so can the code.

## Why it matters

For some problems a recursive function is the most direct transcription of the definition, and therefore the easiest to check. This is especially true of nested, tree-shaped data: phylogenies, genealogies, nested sampling designs, spatial subdivisions. For other problems, a loop does the same job more cheaply. Knowing how recursion works, what it costs and how it fails lets you choose.

## How it works in C++

### Base case and recursive case

Let $D(n)$ be the number of descendants of one founder over $n$ generations when every individual has $k$ offspring. The founder has $k$ offspring, and each of them contributes itself plus its own descendants over $n - 1$ generations:

$$
D(n) = k\,\bigl(1 + D(n - 1)\bigr), \qquad D(0) = 0 .
$$

- **Base case** (lines 10–12): with no generations there are no descendants. The function returns at once, without calling itself.
- **Recursive case** (lines 13–14): the function calls itself with `generations - 1`, a strictly smaller problem, and builds its own answer from the result.

Every recursive function needs both parts, and every chain of calls must reach a base case. Here each call reduces `generations` by one, so starting from any non-negative value the chain ends at 0.

### The call stack

Each call of a function gets its own *frame*: its own copies of the parameters and its own local variables. The frames of the calls that have started but not finished are kept on the *call stack*. When `main` calls `descendants(3, 2)`, that call calls `descendants(2, 2)`, which calls `descendants(1, 2)`, which calls `descendants(0, 2)`. At that moment there are four frames of `descendants` on the stack, each with its own value of `generations`, and three of them are suspended halfway through line 13, waiting for an answer.

`descendants(0, 2)` is the base case and returns 0. Then the stack **unwinds**: `descendants(1, 2)` resumes, computes 2 and returns; `descendants(2, 2)` resumes, computes 6 and returns; finally `descendants(3, 2)` computes 14. That is why the program prints the innermost result first:

```
descendants(1) = 2
descendants(2) = 6
descendants(3) = 14
Total after 3 generations: 14
```

### Recursion and iteration

Anything computed by recursion can also be computed with a loop, and for a simple chain like this one, the loop is the more natural choice:

<Example file="foundations/recursion_vs_loop.cpp" mark="9-24" />

Both functions give the same counts. The loop follows the generations forwards, adding the $k^g$ individuals born in each; the recursion follows the definition backwards. For this problem there is even a closed form, $D(n) = k\,(k^n - 1)/(k - 1)$ for $k \ne 1$, which is the best way of all to compute it and a useful check on both.

The cost of recursion:

- **Overhead per call.** Each call creates a frame, copies its parameters and returns. For a cheap computation this overhead can dominate, so a recursive version is usually somewhat slower than a loop.
- **Limited depth.** The call stack has a fixed size, typically a few megabytes. A recursion a few thousand levels deep is fine; one that is a million levels deep, such as a recursive projection of a population over a million time steps, can exhaust it and crash the program with a *stack overflow*. C++ does not guarantee that the compiler will turn recursion into a loop.

Use recursion where the problem has a branching, nested structure. Use a loop where it is a simple sequence of steps, such as the generations of a simulation.

### Where recursion shines: trees

A phylogeny is naturally recursive: a clade is either a leaf (here, a genus with a known number of species) or a group of smaller clades. Counting the species in a clade is then a recursive function with the leaf as its base case:

The recursive case makes one call per subclade, not just one, and the function neither knows nor cares how deep the tree is. Written with loops alone, the same count needs a hand-managed list of clades still to visit. The tree is stored as a `struct` whose member is a vector of further clades (see <Concept id="structs" /> and <Concept id="std-vector" />), and it is passed by const reference so that no part of it is copied (see <Concept id="const-reference" />).

<Callout kind="pitfall" title="Infinite recursion">
If a chain of calls never reaches a base case, each call adds another frame until the stack is exhausted and the program crashes. This happens when the base case is missing, when the recursive call does not shrink the problem, or when an argument can jump past the base case. `descendants(-1, 2)` is an example: `generations` goes −1, −2, −3, … and never equals 0. Writing the base case as `if (generations <= 0)` closes that gap. Check every recursive function by asking: does every call get closer to a base case, and can it ever skip over it?
</Callout>

## In biological modelling

- **Trees.** Phylogenies, genealogies and cell lineages are trees. Counting tips, computing the total branch length, finding the depth or visiting every node in order are recursive functions with the leaf as the base case. Reading tree files in the Newick format, in which clades are nested in parentheses, is recursive as well.
- **Branching processes.** Expected numbers of descendants, extinction probabilities over a fixed number of generations and the size distribution of a lineage satisfy recursions such as $D(n) = k\,(1 + D(n-1))$. Often the recursion is best used to *derive* a closed form or a loop, and the recursive code serves as a check.
- **Divide and conquer.** Some algorithms split a problem into halves, solve each recursively and combine the results, for example to sort data or search a sorted table (see <Concept id="algorithm-design" />).
- **Not for time steps.** A simulation's time loop should be a loop. Writing $N_t = \lambda N_{t-1}$ as a recursive function is correct, but costly, and over long runs it overflows the stack.

## Common mistakes

- **No base case, or one that can be skipped.** Use conditions such as `n <= 0` rather than `n == 0` when an argument might start below the base case.
- **A recursive call that does not shrink the problem.** Every call must move closer to the base case.
- **Recursion over a long sequence.** Thousands of time steps or individuals in a chain belong in a loop.
- **Recomputing the same subproblem.** A recursion that calls itself twice on overlapping subproblems can take exponentially long. Store results that are needed again, or use a loop that builds them up in order.
- **Passing a large structure by value.** Every frame would hold a copy. Pass trees and vectors by const reference.
