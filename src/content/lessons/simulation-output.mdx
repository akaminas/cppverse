## What it is

A simulation produces a *trajectory*: the state of the model at every time step. In <Concept id="discrete-time" /> that trajectory was stored in a `std::vector` and printed. This lesson writes it to a file that other programs can read: a CSV (comma-separated values) file with

- a few **metadata lines**, starting with `#`, that say what produced the numbers;
- a **header row** that names the columns;
- **one row per time step**, with every value at full precision.

The file is the hand-over point between the simulation, written in C++, and the analysis, usually done in R or Python.

## Why it matters

A result is only as useful as the file it lives in. Three things go wrong surprisingly often:

- **The file cannot be read without manual editing**: columns run together, the header is missing, or explanatory text is mixed into the data.
- **The numbers are rounded**: printed with six digits, two runs that differ in the eighth digit look identical, and a population approaching its carrying capacity appears to reach it.
- **Nobody knows which run it was**: the parameters are in a notebook, or in the source code as it was three versions ago.

A well-written output file prevents all three. It is also the cheapest form of reproducibility: if every file says which program and which parameters produced it, any figure can be traced back to its origin.

### The parts of the program

- **Simulation and output are separate functions.** `simulate` returns the whole trajectory; `writeTrajectory` only writes. You can change the file format without touching the model, and test the model without writing files.
- **`std::ostream&`** is the type of any output stream, so `writeTrajectory` accepts the file stream `out` and would equally accept `std::cout`. Streams cannot be copied, so the parameter is a <Concept id="references">reference</Concept>.
- **Metadata as `#` lines.** Each line is a `key: value` pair, easy to read for a person and for a script. `std::time` gives the current time and `std::put_time` (from `<iomanip>`) formats it, here as UTC in ISO 8601 form.
- **Two precisions.** Parameters are written with `digits10` (15) significant digits, which reproduces any value a person typed, so `2.2` appears as `2.2`. Computed values are written with `max_digits10` (17), the number of digits needed to read back exactly the same `double`. Both constants come from `<limits>`; <Concept id="output-formatting" /> explains them in detail.
- **Checking the result.** `out.close()` writes any remaining buffered data. If the disk is full or the file system fails, the stream records it, so the program checks `out.fail()` after closing and reports an error instead of claiming success.

### One observation per row

A model with several state variables raises a layout question. For the two stages of a juvenile-adult model, the *wide* layout gives each variable a column; the *long* layout gives each value a row and adds a column saying which variable it is:

```text
wide                          long
generation,juveniles,adults   generation,stage,count
0,0,10                        0,juvenile,0
1,41.67,5                     0,adult,10
                              1,juvenile,41.67
                              1,adult,5
```

Both are tidy as long as every row is one observation and every column one variable. The long layout scales better: adding a stage, a replicate or a parameter value adds rows, not columns, and plotting libraries such as ggplot2 and seaborn take it directly (`colour = stage`). The complete simulation in <Concept id="procedural-review" /> writes this layout. (The values in this illustration are rounded; the real file keeps all digits.)

### One file per run

Write each run to its own file, and give the file a name that says what is inside: `beverton_holt_R0-2.2.csv` rather than `output.csv`. Opening an existing file for writing erases it, so a fixed name silently replaces yesterday's results. <Concept id="string-streams" /> shows how to build such names from parameter values, replicate numbers and seeds.

<Callout kind="biology" title="What a deterministic model still needs to record">
The Beverton-Holt model has no randomness, so the same parameters always give the same trajectory, and the seed line says "none". For a stochastic model the seed is essential: without it, a single replicate can never be regenerated. See <Concept id="random-seeds" /> and <Concept id="seed-management" />.

## Reading the file in R or Python

Both languages skip the metadata lines if told which character starts a comment.

```r
# R
traj <- read.csv("beverton_holt_output.csv", comment.char = "#")
str(traj)       # 31 obs. of 2 variables: generation (int), N (num)
plot(N ~ generation, data = traj, type = "b", ylab = "Population size N")
abline(h = (2.2 - 1) * 40, lty = 3)   # carrying capacity K

# the metadata, as a named character vector
meta <- grep("^# ", readLines("beverton_holt_output.csv"), value = TRUE)
meta <- sub("^# [^:]+: ", "", setNames(meta, sub("^# ([^:]+):.*", "\\1", meta)))
as.numeric(meta["R0"])   # 2.2
```

```python
# Python with pandas
import pandas as pd

traj = pd.read_csv("beverton_holt_output.csv", comment="#")
print(traj.tail(3))

with open("beverton_holt_output.csv") as f:
    meta = dict(line[2:].rstrip("\n").split(": ", 1) for line in f if line.startswith("# "))
print(float(meta["R0"]))   # 2.2
```

## In biological modelling

This lesson is the middle link of a chain that every modelling project follows: a model is simulated (<Concept id="discrete-time" />), its output is written to files (this lesson), and the files are analysed and interpreted (<Concept id="output-analysis" />, <Concept id="interpretation" />). The output file is the only part of the chain that outlives the run, so it deserves the most care.

A checklist for every output file:

1. A header row with short column names.
2. One row per observation, including the initial state.
3. Full precision for computed values.
4. Metadata: model, every parameter, initial conditions, seed, program and version, date.
5. A file name that identifies the run, and a new file for every run.

## Common mistakes

- **Writing to `std::cout` and copying from the terminal.** Use a file stream, or at least shell redirection, and keep messages on `std::cerr`.
- **Leaving out generation 0.** The initial condition is part of the trajectory.
- **Rounding on output.** Round in the figure, not in the data.
- **Units or spaces in column names** (`N (individuals)`): they make every analysis script awkward. Put units in the metadata.
- **Parameters only in the source code.** Write them into the file, or better, read them from a <Concept id="parameter-files">parameter file</Concept> and echo them into the metadata.
- **Assuming the write worked.** Check the stream after closing it.
