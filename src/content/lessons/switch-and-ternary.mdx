## What it is

`if` and `else` can express every decision, but two special cases are common enough to have their own syntax. The *conditional operator* `condition ? a : b` chooses between two **values** inside a single expression. The `switch` statement chooses between many **branches** according to the value of an integer, a character or an enumeration, and is the natural way to say "apply whichever event has just happened".

## Why it matters

Both make a frequent pattern shorter and its intent clearer. `?:` lets a parameter that depends on a condition still be `const`. A `switch` over a named list of events reads like the event table of a model, and the compiler can check that no event has been forgotten. Stochastic simulations are built around this: draw which event occurs, then dispatch on it.

## How it works in C++

<Anchor id="conditional-operator" />

### The conditional operator

```cpp
const double growth_factor = rainfall > 600.0 ? 1.3 : 0.8;
```

reads "if rainfall exceeds 600 mm, then 1.3, otherwise 0.8". The condition is evaluated first; then exactly one of the two other operands is evaluated, and its value becomes the value of the whole expression. Because `?:` has three operands it is also called the *ternary* operator.

The point of an expression, as opposed to an `if` statement, is that it can appear where a value is needed. With `if` the growth factor could not be `const`, because it would have to be declared first and assigned afterwards. With `?:` it is initialised once, correctly, and protected from accidental change. The same property makes `?:` useful inside output:

<Example file="foundations/ternary_wet_year.cpp" mark="10,16,18" />

Three rules to remember:

- **Parenthesise it.** `?:` has very low precedence, lower than `<<`. `std::cout << n == 1 ? "a" : "b";` is parsed as `(std::cout << n) == 1 ? …` and does not compile. Inside an output statement, always put the whole conditional expression in parentheses.
- **Both alternatives need a common type.** In `n > 0 ? 1 : 0.5` the `1` is converted to `double`, so the expression is a `double` whichever branch is taken.
- **Keep it simple.** `?:` is for choosing between two values. Nested conditional operators and alternatives with side effects are much easier to read as an `if` statement.

### The switch statement

A `switch` evaluates one expression and jumps to the `case` label with the same value:

<Example file="foundations/switch_events.cpp" mark="18-31" />

The parts:

- **The controlling expression**, `switch (e)`, must have an integer, character or enumeration type. Doubles and strings are not allowed.
- **Case labels**, `case Event::birth:`, must be constants known at compile time, and no two may have the same value. A label is only a *target*: it is not a test that is carried out in turn, and it marks a position rather than enclosing a block.
- **`break`** leaves the `switch` and continues after its closing brace. Without it, execution runs on into the statements of the next case (see below).
- **`default:`** is the target when no label matches. It is optional; without it, an unmatched value simply skips the whole `switch`.

A `switch` is the tidy replacement for a long ladder of `if (code == 1) … else if (code == 2) … else if (code == 3) …`, in which the same variable is compared with one constant after another. It tests for equality with fixed values only, though. A rule such as "adult at 400 degree-days or more" is a range and needs an `if`/`else if` chain (see <Concept id="if-else" />).

### enum class: giving events names

The events above are not coded as 0, 1 and 2 but as an *enumeration*:

```cpp
enum class Event { birth, death, immigration };
```

`enum class` creates a new type, `Event`, whose only values are the three listed enumerators, written `Event::birth` and so on. Compared with plain integer codes this has three advantages: the code says what it means, an `Event` cannot be mixed up accidentally with a population size or an index, and the compiler knows the complete list. With `-Wall`, a `switch` on an enumeration that has no `default` and misses one of the enumerators produces a warning. If a fourth event, say `Event::emigration`, is added to the model later, the compiler points at every `switch` that does not yet handle it. For that reason, a switch over an `enum class` usually lists every enumerator and has no `default`.

### Fall-through, stacked labels and [[fallthrough]]

Because labels are only jump targets, a case without `break` continues into the next case. Usually that is a bug. Sometimes it is exactly what is needed:

<Example file="foundations/switch_stage_tally.cpp" mark="19-37" />

Two techniques appear here:

- **Stacked labels.** `case 'A': case 'a':` puts two labels on the same position, so both codes run the same statements. There is nothing between the labels to fall through.
- **Deliberate fall-through.** An adult has also passed through the pupal and larval stages, so after counting it as an adult the code continues into the pupa and larva cases. The C++17 attribute `[[fallthrough]];` placed just before the next label states that this is intended.

GCC's `-Wextra` warns about every fall-through between non-empty cases that lacks `[[fallthrough]]`. That is how accidental fall-through, the classic `switch` bug, is caught: a missing `break` produces a warning, an intended one is annotated.

### Variables inside a case

A variable declared directly under a case label is in scope for the rest of the `switch`, and jumping to a later label past its initialisation is an error. Give such a case its own block:

```cpp
case Event::death: {
    const int lost = 1;   // local to this block
    n -= lost;
    break;
}
```

<Callout kind="manual" title="Limits and newer features">
The manual states that a `switch` may have "no more than 16384 cases". That number is the *minimum* the standard recommends that every compiler support, not a maximum; real compilers accept far more. The manual's examples switch on integers and characters; `enum class` (C++11) and `[[fallthrough]]` (C++17), used here, are later additions that make switches safer.
</Callout>

## In biological modelling

- **Event dispatch.** In a stochastic birth–death–immigration model the simulation repeatedly draws which event happens next and when (the <Concept id="gillespie" /> algorithm), then applies its state change. The `switch` over an `enum class Event` above is exactly that second half, with a fixed sequence standing in for the random draws.
- **Stage-specific rules.** Once an individual's stage is stored as an enumeration, a `switch` selects its survival probability, its diet or the output label.
- **Reading coded data.** Field sheets and data files use letters or numbers for categories. A `switch` with stacked upper- and lower-case labels and a counting `default` turns them into model categories and catches unreadable codes rather than ignoring them.
- **Conditional parameters.** `const double r = is_wet_year ? r_wet : r_dry;` keeps a year-dependent parameter `const`.

## Common mistakes

- **A forgotten `break`.** Execution falls into the next case. Compile with `-Wextra`, and mark intended fall-through with `[[fallthrough]];`.
- **Expecting a switch to test ranges or doubles.** It compares an integral or enumeration value with constants; use `if`/`else if` for thresholds.
- **A `default` on an `enum class` switch that hides a missing case.** When every enumerator is listed, leave the `default` out so that the compiler can tell you when a new one is added.
- **Declaring a variable directly under a label.** Wrap the case in braces.
- **An unparenthesised `?:` in an output statement.** Put the whole conditional expression in parentheses.
