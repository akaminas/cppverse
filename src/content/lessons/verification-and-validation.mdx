## What it is

Two different questions stand between a simulation and a scientific claim:

- **Verification**: does the code implement the model correctly? This is a question about mathematics and software. It can be answered without any data from nature.
- **Validation**: does the model describe the biological system well enough for its purpose? This is a question about nature, and only data can answer it.

A common shorthand is that verification asks "are we solving the equations right?" and validation asks "are we solving the right equations?". The order matters. A model cannot be validated with code that does not implement it: if a simulation disagrees with data, you need to know that the disagreement comes from the model, not from a bug.

## Why it matters

Simulation code fails silently. A program with a wrong sign, a sequential update where a simultaneous one was intended, or a step size that is too large still produces plausible-looking curves. The host–parasitoid example of <Concept id="update-order" /> is the cautionary tale: one reordered line turns persistent cycles into a stable equilibrium, and nothing in the output looks wrong.

Verification is how you earn the right to interpret the output. It also protects against a subtler failure: a bug that pushes results towards what you expected is far less likely to be found than one that does the opposite, because nobody investigates a result they like.

## How it works in C++

Every verification test compares the simulation with something known *independently of the code*. There are five main kinds.

### Closed-form benchmarks

Some models, or special cases of them, have exact solutions. The Beverton–Holt recurrence $N_{t+1} = R_0 N_t / (1 + N_t/M)$ has one:

$$
N_t = \frac{K N_0}{N_0 + (K - N_0)\,R_0^{-t}}, \qquad K = (R_0 - 1)\,M ,
$$

where $N_t$ is the population in generation $t$, $R_0$ the growth factor at low density, $M$ the density at which that factor is halved, and $K$ the equilibrium. A correct implementation agrees with it to rounding error, about $10^{-15}$ relative:

<Figure id="bh-verification" />

The logistic ODE, $dN/dt = rN(1 - N/K)$, has the exact solution $N(t) = K N_0 e^{rt} / \big(K + N_0 (e^{rt} - 1)\big)$, which <Concept id="euler" /> and <Concept id="runge-kutta" /> use as their benchmark. Test as many parameter regimes as the formula covers: growth and decline, small and large initial values.

### Invariants and assertions

An *invariant* is a property that must hold at every step. Population sizes are never negative. In the SIR model in proportions, $S + I + R = 1$ at all times, because infection and recovery only move individuals between classes; the example program `ode/sir_rk4.cpp` records the largest drift of this sum. In a stochastic simulation, every event must change the state by exactly its stoichiometry.

The cheapest way to check an invariant is an `assert` (<Concept id="debugging" />): `assert(N >= 0.0);` stops the program with a message if the condition is ever false. Assertions document assumptions and catch violations where they happen, not thousands of steps later. They are removed when the program is compiled with `-DNDEBUG`, so never put code with side effects inside one.

Choose invariants that a bug would actually break. Every Runge–Kutta method preserves linear invariants such as $S + I + R$ exactly, apart from rounding, whatever the step size. The SIR conservation check therefore catches a wrong right-hand side, such as a term missing from one equation, but says nothing about whether the step is small enough. For that you need the next test.

### Convergence order

A numerical method of order $p$ has a global error that shrinks like $C h^p$ as the step $h$ shrinks (<Concept id="numerical-error" />). This prediction is a powerful test: halving $h$ should divide the error by $2^p$. The *observed order* from errors $E(h)$ and $E(h/2)$ is

$$
p_{\text{obs}} = \log_2 \frac{E(h)}{E(h/2)} .
$$

<Figure id="verification-and-validation-convergence" />

On logarithmic axes the three methods give straight lines of slopes 1, 2 and 4. A method whose observed order is wrong is wrong, even if its answers look reasonable: an "RK4" that converges at order 2 contains a mistake in its stages. The test needs the exact solution, or a reference solution computed with a much smaller step. Very large steps are outside the asymptotic regime (Euler's observed order at $h = 1$ is not 1), and very small steps hit rounding error, so test in between.

### Statistical tests against exact results

A stochastic simulation never reproduces an exact result exactly; it should agree with it *within sampling error*. For the linear birth–death process with birth rate $b$ and death rate $d$ per individual, Kendall (1948) derived the probability that a population started from $N_0$ individuals is extinct by time $t$:

$$
p_0(t) = \left[\frac{d\,\big(e^{(b-d)t} - 1\big)}{b\,e^{(b-d)t} - d}\right]^{N_0}, \qquad b \ne d .
$$

If $n$ independent replicates give an observed fraction $\hat{p}$ of extinct populations, the standardised difference

$$
z = \frac{\hat{p} - p_0}{\sqrt{p_0 (1 - p_0)/n}}
$$

is approximately standard normal when the code is correct. Values of $|z|$ above 2 happen about one time in twenty by chance; values above 4 almost never (about six times in a hundred thousand). The figure tests the extinction fraction at twenty time points:

<Figure id="verification-and-validation-kendall" />

The example program `stochastic/birth_death_gillespie.cpp` (<Concept id="gillespie" />) makes the same comparison for the mean and the extinction probability at one time. Two details make such tests trustworthy. Fix the seed, so that a failing test can be rerun and debugged. And set the threshold before looking: with many tests, some will exceed 2 by chance, so a test suite that must pass every time uses a threshold of 4 or more, together with enough replicates that a real bug would produce a much larger $z$.

Each test has a tolerance chosen in advance: $10^{-10}$ relative for an exact formula evaluated in floating point, 0.1 for an observed order. The output is fully deterministic, so it can itself be compared with a stored copy: a *regression test* (<Concept id="testing-reproducibility" />).

### Independent re-implementation

A strong form of verification is to implement the same model twice, independently, and compare. This site does it: every model in the browser laboratories is written in TypeScript, and the C++ example programs implement the same models separately. A script, `scripts/compare-cpp-benchmarks.ts`, compiles and runs the C++ programs and compares their output with the TypeScript code and with the exact results.

The comparison is honest about what each kind of model allows:

- **Deterministic models** (Beverton–Holt, host–parasitoid, the stage matrix, the ODE integrators) must agree closely: typically to a relative tolerance of $10^{-9}$, and elsewhere to the number of digits a program prints. They are not required to agree to the last bit, because the two languages may evaluate `exp` and `pow` slightly differently and accumulate rounding in different orders; but any real difference in the model would be many orders of magnitude larger.
- **Stochastic models** are never compared trajectory by trajectory. The browser uses a different generator (`xoshiro128**`) from the C++ programs (`std::mt19937_64`), and C++ standard libraries are free to implement distributions differently. Instead, the means and extinction fractions of both must lie within four standard errors of Kendall's exact values, and the individual-based model must approach its mean-field limit.

Re-implementation catches coding errors well. It is weaker against conceptual errors: two programs written from the same misunderstanding agree perfectly. If both implementations update hosts before parasitoids, they will agree on the wrong dynamics. That is why re-implementation complements, rather than replaces, tests against independent mathematics.

## In biological modelling

### Validation: does the model describe the system?

Verification ends with a model you can trust to mean what it says. Validation asks whether what it says is true of the organisms. There is no single test, and a model is never validated in general, only for a purpose: a model adequate for predicting the size of a fish stock next year may be useless for predicting its response to a doubling of fishing effort.

**Comparing with data.** The most direct test compares model output with observations of the quantities the model predicts. For a stochastic model the comparison is distributional: observed data should look like one plausible replicate, so ask where the observations fall among the replicate distribution, not whether they match the mean. Include observation error: counts of animals are themselves noisy estimates.

**Pattern-oriented modelling.** A model that reproduces one pattern, such as a population time series, may do so for the wrong reasons; with enough parameters, many structures can fit one curve. Grimm and colleagues (2005) argue for testing a model against *several* patterns observed at different levels and scales at once, for example a population's size, its spatial distribution and its age structure. Each pattern rules out some model structures and parameter values. A model that reproduces several patterns it was not tuned to is much more credible.

**Out-of-sample tests.** A model fitted to data will match those data to some degree almost regardless of its truth. The stronger test is prediction of data not used in fitting: later years, another site, another treatment. The shift from fitting to predicting is the single most informative step in validation.

**Model comparison.** Often the question is not "is this model true?" but "which of these models is better supported?". When models are fitted by maximum likelihood, information criteria trade goodness of fit against complexity. Akaike's criterion is

$$
\mathrm{AIC} = 2k - 2 \ln \hat{L},
$$

where $k$ is the number of estimated parameters and $\hat{L}$ the maximised likelihood of the data under the model. Lower is better; differences of a few units matter, and the absolute value does not. The Bayesian information criterion, $\mathrm{BIC} = k \ln n - 2\ln\hat{L}$ for $n$ observations, penalises parameters more heavily. For many stochastic simulation models the likelihood cannot be written down; approximate Bayesian computation and synthetic likelihood methods then compare simulated and observed summary statistics instead.

### What validation can and cannot establish

Validation can show that a model is *adequate* for a purpose, within a range of conditions, and better supported than named alternatives. It cannot show that a model is *true*. Agreement with data is consistent with many models, including ones nobody has thought of, and a model validated under present conditions may fail under conditions it was never tested against. Disagreement is more informative than agreement: once verification has excluded bugs, a mismatch with data points to a missing or mistaken process, which is often the most interesting result a model produces.

Report validation as what was done: which data, which patterns, which alternatives, and how the model performed. Readers can then judge for themselves how far to trust the model's predictions (<Concept id="interpretation" />).

## Common mistakes

<Callout kind="pitfall" title="Tuning the test until it passes">
If a statistical test fails, it is tempting to try another seed, then another, until one passes. That turns a test into a ritual. Fix the seed and threshold in advance; if the test fails, investigate; if it was chance, you will see the next time with more replicates.
</Callout>

- **Testing only the default parameters.** Many bugs appear only in some regimes, such as $R_0 \lt 1$, an empty population, or a step size near the stability limit. Test edge cases deliberately.
- **Tolerances that are too loose.** A tolerance of 1 % on a closed form evaluated in double precision would pass a large class of real errors. Match the tolerance to the expected error.
- **Calling calibration validation.** Adjusting parameters until the model matches data is fitting. The same data cannot then serve as an independent test.
- **Validating the mean of a stochastic model.** A model whose mean matches observed averages may still have the wrong variance, the wrong extinction risk or the wrong autocorrelation.

<summary>Worked answer for exercise 2</summary>
At $R_0 = 1$ the equilibrium is $K = 0$, and the general formula becomes $0 \cdot N_0 / (N_0 - N_0) = 0/0$, which is NaN in floating point. Every comparison with NaN is false, so the test reports FAIL, which is the right outcome for a broken benchmark. With $R_0 = 1$ the recurrence is $1/N_{t+1} = 1/N_t + 1/M$, so $N_t = N_0/(1 + N_0 t/M)$; add `if (R0 == 1.0) return N0 / (1.0 + N0 * t / M);` at the top of `bevertonHoltExact`.
